Architecture case study

Vault Harness

A payment harness that lets an AI agent pay online without ever seeing, storing, or remembering a card number — card data is sealed in the owner's browser and only ever exists in clear inside an isolated enclave, for one payment.

Saraswat Das — Tech Lead · Solo design & build, Oct–Nov 2026
7 real payments confirmed on statement 219 tests passing offline 0 leaked card numbers Nitro enclave: prepared, not run on AWS Passkey: software authenticator only
01

The problem

Letting an LLM agent "just pay for something" is a credential-isolation problem before it is an AI problem. The moment a card number or CVC touches a prompt, a tool call, a log line, or a browser profile, it can leak through prompt injection, a stray echo, or a crash dump. The brief: build a harness where the agent proposes a payment, but never holds a secret — isolation has to be structural, enforced by code and a hardware boundary, not by asking the model nicely.

High-level design — trust zones

Six zones, each with a hard rule about what it may and may not hold. The card is in clear in exactly two places: the owner's browser for the instant it's typed, and the enclave for one payment.

Low-level design — one payment, end to end

The sequence below is what actually runs for a real payment: the agent never appears between the card and the money. 

sequenceDiagram
  participant Owner
  participant Agent
  participant Guard
  participant Browser as Kernel browser
  participant Enclave
  participant Stripe

  Owner->>Owner: type card once (seal.js: X25519 → HKDF → AES-GCM)
  Owner->>Enclave: ciphertext {epk, nonce, ct, aad=card_id}
  Agent->>Guard: JSON proposal (merchant, amount, currency)
  Guard->>Guard: freeze? → policy (cap/merchant/currency) → velocity → risk score
  Guard->>Owner: Touch ID challenge (amount ≥ auto-limit)
  Owner->>Enclave: signed approval assertion
  Guard->>Enclave: issue_placeholder() — Visa-shaped, Luhn-valid, 10 min, bound to merchant+amount
  Enclave->>Browser: placeholder card
  Browser->>Stripe: fills checkout with placeholder
  Stripe->>Enclave: tokenization request (intercepted)
  Enclave->>Enclave: _gate (host+path allowlist) → _open card → _swap in real PAN
  Enclave->>Stripe: real card, https, api.stripe.com/v1/payment_methods only
  Stripe-->>Enclave: PaymentMethod id
  Enclave-->>Guard: masked result (last4, brand) — card forgotten
  Guard->>Guard: post-check: charge == approved amount, else halt

The guard's own decision pipeline, run before anything above the "issue placeholder" line is allowed to happen:

1
Freeze checkCard or agent frozen? Refuse immediately — freezing never needs a fingerprint.
2
PolicyPer-purchase cap, merchant/currency allowlist, schema validation — unknown JSON fields rejected outright.
3
VelocityPayments/min, /hour, /day and spend/hour, /day — checked on the host and re-reserved inside the enclave.
4
Risk scoreReal-time score against the last 200 payments' median; escalates to human approval above a threshold.
5
Human approvalTouch ID above the auto-approve limit, verified inside the enclave, not by the host.
6
Post-checkCharged amount must equal the approved amount, or the run halts and alerts.

Known weaknesses — stated, not hidden

A security design is only as credible as the gaps it admits. These are tracked, not discovered by a reviewer:

The enclave isn't hardware-isolated yet. It's a separate program and a Docker image; the AWS Nitro build, attestation and KMS plan are written and tested only against synthetic documents.
Budget and velocity counters live in enclave memory. A host that can restart the enclave resets them — rollback-proof, sealed counters aren't built.
Touch ID is tested against a software authenticator, not yet a real device.
Per-payment CVC is the real scaling limit. Stripe and PCI DSS forbid storing one; a processor or network token (no CVC needed) is the next step and isn't built.
The local agent API is unauthenticated — safe only because the host is trusted; production needs a separate, authenticated agent identity.
