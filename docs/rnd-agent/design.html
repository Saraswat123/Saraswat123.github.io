STEM Activity Monitoring

R&D - Agent

One pipeline, three checks: did the campus report it, did the sheet show it, did the Drive evidence land. Built for 10 campuses, one WhatsApp group, no manual cross-referencing.

Parser + cross-check: 20/20 tests passing WhatsApp gateway: linked and connected Live test: scheduled for next morning report

User flow

The exact chain: WhatsApp report in, Moltis gateway reads it, Groq or OpenRouter does the language step, Sheet API writes it to the daily log, the STEM agent reviews Drive + the curriculum sheet against it, cross-check verifies, the sheet gets updated, scoring matrix closes the loop.

09

Drive image recognition

Default behavior is presence-only: did a file land in the month's folder, when, how many. No vision model reads the photo content by default — Rysen's students are in these photos, and opening that up needs its own explicit guardrail, not a side effect of counting files.

By design — presence-check only

Guardrails in place

Scope

  • DM policy: disabled — never responds to or logs private messages.
  • Group policy: allowlist — processes exactly one confirmed group JID, nothing else.
  • Mention mode: none — never sends a visible reply, in this group or any other, regardless of policy.
  • Every policy change made through the account's own stored config, verified by reading it back before trusting it.

Sheet safety

  • Writes are additive only — new rows, new columns. Never edits an existing educator-entered cell.
  • Cell values starting with = + - @ get prefixed before writing, so nothing can execute as a formula (same rule used on the meeting-minutes pipeline).
  • Meeting-notes flags are rule-based, not model-guessed — no fabricated "this was resolved" claims on a real log.

Weekly review scope

  • Runs once a week against the full month's data, not live per message — reduces false alarms from a campus simply being mid-week.
  • Output is a flag list for a human to read, never an automatic correction written into anyone's tracker row.
  • Every flag names the exact rule that fired (completion vs. Drive, activity vs. WhatsApp) — no unexplained score.

Drive image recognition

  • Off by default. The agent checks that a file exists for the month — filename, timestamp, count — and stops there.
  • No face recognition, no student identification, no model reading the image itself, under any configuration this agent ships with.
  • If content-level checking (e.g. "does this photo actually show a robotics session") is ever wanted, it needs its own explicit sign-off and its own guardrail card — not a quiet addition to the presence check.

Eval audit

How accuracy gets measured before this runs unattended — not a one-time check, a recurring one.

Golden set

  • Once a week of live WhatsApp reports exists, hand-label the correct Campus / Educator / Resources Ready / Support Required fields for every message that week.
  • Run parse_whatsapp.py against the same messages, diff its output against the hand-labeled set.
  • Track two numbers: extraction accuracy (fields correct ÷ fields present) and miss rate (real reports the parser didn't recognize at all).

Flag precision

  • For every flag cross_check.py raises, confirm by hand whether it was a real gap or a false alarm (e.g. Drive upload delayed, not missing).
  • A false-positive rate above a set threshold pauses automatic flagging for that rule until the logic is corrected — never let a noisy rule train you to ignore all flags.
  • Re-run this audit after any change to the parser or the cross-check join logic, not just on a fixed schedule.

Known limitations

Found by testing against the real group today, not assumed in advance.

Limitation What it means
Group JID only appears after a new message Moltis doesn't bulk-sync dormant chat history — a group with no activity since pairing stays invisible locally until someone posts in it.
Self-sent messages aren't logged The access-log table only captures inbound messages that need a routing decision. A message you send yourself never triggers it.
Group message bodies log empty Direct/individual messages capture full text; group messages so far have logged with an empty body in every case seen. Likely a built-in privacy boundary, not a policy setting — the webhook route is the planned fix.
No CLI send or join yet Both are present in the CLI but return "not yet implemented" in this build. Sending test messages or joining groups has to happen from the phone.
Campus name spelling drift Drive folder names and sheet tab names don't always match exactly (for example two spellings of the same town) — normalized in the parser, worth re-checking if a new campus is added.
